# Client localization

Native client localization is owned by `packages/flutter_app/lib/ui/localization.dart` and JSON catalogs under `packages/flutter_app/assets/locales`. Website localization is a separate system described in [website-i18n](website-i18n.md).

The native locale list is English, Arabic, Spanish, French, Japanese, Korean, Brazilian Portuguese, Russian and Simplified Chinese. The loader maps Portuguese to `pt-BR` and Chinese to `zh-CN`, loads the selected and English catalogs, and caches catalog futures.

Use `tr(context, key, args: ...)` for client-owned copy. Keys use dotted lookup; plural forms use the locale's `Intl.pluralLogic` suffix. Interpolation uses `{{name}}`. Lookup falls back from the selected plural/key to English and finally the key, so a missing translation is not an excuse to change protocol strings or user content.

Translate labels, controls, empty states, confirmation copy and local wrappers. Do not translate provider output, persisted identifiers, paths, API tags or raw diagnostic evidence. Preserve placeholders and plural semantics across catalogs. Provider/forge-specific nouns must match the actual selected service rather than be inferred from English UI text.

Changing locale must not recreate sessions, reset drafts, lose host selection or mutate daemon configuration. Respect right-to-left layout, text expansion, text scaling and accessibility labels. Native controls, errors and retry states need translation as well as the happy path.

Executable React plugin translations are not a native UI extension mechanism. Optional backend plugins may return data, but the Flutter client does not load a React translation/component runtime.

Verify catalogs and visible flows on the actual native client. A website locale check or a former TypeScript app translation test does not establish native coverage. See [testing](testing.md) for recorded evidence and missing platform execution.
